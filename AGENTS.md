# NeuroSync Engineering and Scientific Integrity

These instructions apply to all work in this repository. If a project requirement conflicts with convenience, preserve reproducibility, provenance, and scientific accuracy.

## Project scope

NeuroSync investigates whether physiological and behavioral signals can help estimate human-robot collaboration states and inform assistance. Separate software capability from scientific evidence and from any claim about deployed robot behavior.

## Scientific integrity

- Label simulated/synthetic data conspicuously in filenames, metadata, APIs, plots, notebooks, and documentation. Never present it as human data.
- Never fabricate participants, recordings, annotations, metrics, experimental outcomes, citations, or validation. Report only results generated by a documented procedure, including failures and uncertainty where relevant.
- Do not claim clinical validity, diagnostic utility, readiness for deployment, or generalization beyond the evaluated data and protocol.
- EEG features are measurements or derived statistics. Do not describe them as directly revealing emotion, intention, attention, trust, or collaboration state.
- Correlation, coherence, phase locking, or other association between people does not establish interpersonal synchrony or causal influence. Name the statistic, preprocessing, windowing, controls, uncertainty, and alternative explanations.
- Keep hypotheses, assumptions, operational definitions, and limitations explicit. Distinguish exploratory analyses from confirmatory evaluation.
- For ML, define the target and annotation source; use leakage-resistant participant/session splits when applicable; compare with simple baselines; report class balance, uncertainty, and suitable metrics. Fit transforms only on training data. Do not tune on held-out evaluation data.
- Document missing data, artifact handling, multiple comparisons, filtering choices, units, and sampling assumptions. Avoid unsupported universal thresholds or cherry-picked plots.

## Human data and privacy

- Do not add real human recordings or identifying metadata without an explicit, documented data-governance basis and appropriate consent and institutional approvals where required.
- Keep raw/private data out of Git. Use documented local data paths and small synthetic fixtures for tests. Never put participant identifiers in logs, filenames, notebook outputs, or screenshots.
- Treat any future behavioral, physiological, or interaction data as sensitive. Minimize collection, access, retention, and derived data exposure.

## Engineering standards

- Target Python 3.11 as declared by the project. Declare dependencies and optional feature groups in project metadata; do not rely on ambient/global packages.
- Use a modular `src/` package, typed public interfaces where useful, focused functions, clear docstrings, and explicit configuration. Keep notebooks for exploration and visualization; put reusable logic in the package.
- Make stochastic generation reproducible through explicit random generators/seeds. Avoid hidden global state and implicit downloads.
- Validate input shape, channel metadata, units, sampling frequency, timestamps, and event alignment at boundaries. Fail loudly and informatively rather than silently changing scientific data.
- Preserve provenance and processing parameters in outputs. Use deterministic, inspectable transformations and document algorithmic choices.
- Tests should cover contracts, edge cases, deterministic behavior, and known signal properties. Synthetic tests validate code behavior, not human neuroscience hypotheses.
- Keep tests fast and isolated; do not require network access or private datasets. Do not add dependencies without a clear need.
- Keep generated outputs, caches, credentials, virtual environments, and raw data out of version control. Never commit secrets.
- Update `DEVELOPMENT_LOG.md` for meaningful work, decisions, checks, and limitations. Update `ROADMAP.md` when milestone scope changes.
- Do not claim checks passed unless they were run in the declared project environment; report the exact commands and material environment limitations.

### Module responsibilities

- `config.py`: validated, serializable parameters and seed/config provenance; no hidden defaults for scientific choices.
- `data/schema.py`: contracts for signals, channels, events, time bases, and provenance; distinguish synthetic from real sources explicitly.
- `data/synthetic_eeg.py`: seeded two-participant simulated EEG-like generation with documented assumptions, component provenance, and no claim to physiological realism beyond those assumptions.
- `preprocessing/raw.py`: validates synthetic channel, unit, sampling, time, and provenance contracts and creates separate MNE Raw objects for each participant.
- `preprocessing/filtering.py`: explicit filtering/reference operations, parameterized and documented with their effects and limitations.
- `preprocessing/epochs.py`: event-locked windowing with clear boundary and baseline conventions.
- `features/quality.py`: signal-quality summaries and checks; these are not cognitive-state labels.
- `features/spectral.py`: Welch PSD, trapezoid-integrated absolute/relative band power, Shannon entropy, and channel summaries with units, windowing, source provenance, and edge checks; excludes channels already marked bad and does not automatically diagnose channel quality.
- `collaboration/labels.py`: future operational label definitions and annotation provenance; no labels inferred from EEG without validated protocol.
- `collaboration/alignment.py`: future timestamp alignment of EEG, behavior, task events, and robot logs with clock assumptions exposed.
- `modeling/baselines.py`: interpretable reference predictors and simple statistical baselines.
- `modeling/evaluation.py`: participant/session-aware splits, leakage controls, metrics, and uncertainty reporting.
- `modeling/multimodal.py`: future fusion of EEG and behavioral/task features, only after data and labels support it.
- `simulation/task.py`: future PyBullet task/environment definitions and measurable task outcomes.
- `simulation/assistance.py`: future inspectable assistance policies and policy evaluation; never equate simulation success with real-world safety.
- `visualization/`: reusable plots with units, provenance, and uncertainty; notebooks should call these package functions.
- `notebooks/`: reproducible research narratives and visual exploration, not the only location of reusable logic.
- `tests/`: deterministic contract and algorithm tests using synthetic fixtures; test success is not scientific validation.
- `configs/`: version-controlled experiment settings with data source and seed; exclude private data and secrets.

## Change discipline

Before adding a research feature, state the question it addresses, required data and labels, assumptions, validation method, and failure modes. Implement the smallest reviewable milestone. Preserve the user's instruction to review the plan before implementation; do not begin pipeline implementation until that review is received.
